# AGENTS.md — Карта процессов, веток действий и субагентов

> Оперативная карта харнеса «ЖКХ-Агент». Как связаны скрипты, ветки решений и
> роли субагентов. Работает вместе с `CLAUDE.md` (правила) и `claude-progress.md`
> (трекинг). Принцип: **Humans steer. Agents execute.**

## 1. Общий поток (pipeline)

```
                 ┌─────────────────────────────────────────────┐
 Входящее   ───► │ classify_input.py  (Classify-and-act)       │
 (текст/PDF/фото)│  → категория + ветка действий               │
                 └───────────────┬─────────────────────────────┘
                                 │
        ┌────────────────────────┼───────────────────────────┐
        ▼                        ▼                            ▼
  [квитанция]              [претензия/приказ]           [объявление ОСС]
  verify_invoice.py        подготовка ответа            проверка кворума
  (Loop-until-done)        Adversarial verification     (ст. 44–48 ЖК РФ)
        │                        │                            │
        └───────────► переплата/нарушение? ──► генерация документа
                                 │
                    Adversarial verification (Агент №1 ↔ Агент №2)
                                 │  (цикл до 0 критических замечаний)
                                 ▼
                    send_for_approval.py  (Human-in-the-Loop)
                                 │
                          [человек одобряет]
                                 ▼
                    отправка (заказное / ГИС ЖКХ / e-mail)
```

Фоновая ветка: `monitor_tariffs.py` обновляет `data/tariffs.json` и сигналит об
изменениях законодательства/тарифов.

## 2. Паттерн 1 — Classify-and-act (сортировка входящих)

**Скрипт:** `scripts/classify_input.py`
**Вход:** текст, PDF-квитанция, фото уведомления (путь к файлу или stdin).
**Выход:** JSON `{category, confidence, signals, next_action}`.

### Ветки действий по категориям

| Категория | Признаки | Ветка действий |
|---|---|---|
| `invoice` (квитанция ЖКУ) | «лицевой счёт», «начислено», строки ГВС/ХВС/отопление/содержание, период, ИПУ/ОДН | → `verify_invoice.py`: сверка с `tariffs.json`, поиск переплат и навязанных услуг |
| `pretension` (досудебная претензия/требование от УК) | «претензия», «требование», «задолженность», «в течение … дней», реквизиты УК | → подготовка мотивированного ответа; проверка основания долга (договор управления, ОСС); Adversarial verification |
| `court_order` (судебный приказ) | «судебный приказ», «мировой судья», «взыскать», «№ дела» | → **СРОЧНО**: срок на возражения — 10 дней со дня получения (ст. 128–129 ГПК РФ). Готовим возражения относительно исполнения приказа. Эскалация человеку немедленно |
| `notice_board` (объявление в подъезде / уведомление ОСС) | «уведомление», «общее собрание», «собственники», «повестка», «голосование» | → проверка легитимности: кворум, повестка, сроки уведомления (ст. 45 ЖК РФ), форма протокола |
| `service_cutoff` (уведомление об ограничении/отключении) | «ограничение», «приостановление», «отключение», «задолженность» | → проверка законности: наличие судебного решения, порядок и сроки предупреждения (разд. XI ПП № 354). Незаконная угроза → жалоба в ГЖИ/прокуратуру |
| `unknown` | не распознано | → эскалация человеку с запросом уточнения/недостающего документа |

> Классификатор эвристический (ключевые слова/паттерны). Уверенность ниже порога
> → категория `unknown` и эскалация человеку. Агент **не домысливает** содержание.

## 3. Паттерн 2 — Loop-until-done (сверка тарифов в квитанции)

**Скрипт:** `scripts/verify_invoice.py`
**Идея:** построчно сверять начисления квитанции с официальными тарифами региона
из `data/tariffs.json` **в цикле до сходимости** — пока каждая строка не будет
либо подтверждена, либо помечена как расхождение с расчётом переплаты.

Алгоритм итерации:
1. Распарсить строки квитанции (услуга, объём, тариф, начислено).
2. Для каждой строки: сопоставить услугу с эталоном в `tariffs.json`.
3. Пересчитать ожидаемую сумму `объём × официальный_тариф`.
4. Сравнить с фактически начисленным (допуск округления).
5. Классифицировать: `ok` | `overcharge` (превышение тарифа) |
   `no_oss` (услуга без решения ОСС) | `unknown_service` | `missing_tariff`.
6. Повторять, пока все строки не получат финальный статус (нет `pending`).
7. Итог: суммарная переплата + перечень нарушений со ссылками на НПА.

Разграничение (см. CLAUDE.md §2.3): ресурсы (ПП № 354, тариф РЭК) vs
содержание/управление (ст. 156 ЖК РФ, ПП № 491, решение ОСС).

## 4. Паттерн 3 — Adversarial verification (состязательный генератор документов)

Два субагента в цикле. Запускается для **любого** исходящего юридического
документа. Ниже — готовые промпты (подставить `{...}`).

### 4.1. Агент №1 — Юрист-Истец (составитель)

```
Роль: юрист, представляющий интересы собственника помещения в МКД.
Задача: составить {тип_документа: претензию / жалобу в ГЖИ / исковое заявление}
к УК по нарушению: {описание_нарушения}.

Исходные данные (только факты из документов, ничего не выдумывать):
{факты, суммы, даты, реквизиты сторон, ссылки на приложения}

Требования к тексту:
- Структура и реквизиты — строго по CLAUDE.md §5 (претензия §5.1 / иск §5.2).
- Каждое утверждение — со ссылкой на конкретную статью/пункт НПА
  (ЖК РФ, ПП № 354, ПП № 491, ЗоЗПП, ГПК РФ).
- Требования — по пунктам, с суммами и сроком.
- Никакой запрещённой лексики (CLAUDE.md §1.3).
- Если данных/доказательства не хватает — явно перечислить пробелы, не домысливать.

Выдай: (1) текст документа; (2) перечень использованных доказательств;
(3) список выявленных пробелов в доказательной базе.
```

### 4.2. Агент №2 — Оппонент (Юрист УК)

```
Роль: юрист управляющей компании — процессуальный оппонент. Твоя цель —
«развалить» документ собственника до суда, найдя все слабые места.

Проанализируй документ:
{текст_документа_от_Агента_1}

Найди и перечисли по пунктам:
1. Процессуальные дыры (подсудность, сроки исковой давности/на возражения,
   досудебный порядок, надлежащий ответчик, госпошлина).
2. Недоказанные факты (утверждения без ссылки на приложение/документ).
3. Неверные или неактуальные ссылки на НПА (отменённые/неприменимые нормы).
4. Логические противоречия и завышенные/необоснованные требования.
5. Ошибки в расчётах сумм, неустойки, штрафа.

Для каждого замечания укажи критичность: КРИТИЧНО / СУЩЕСТВЕННО / МЕЛКОЕ.
В конце — вердикт: «ГОТОВ К СУДУ» (если 0 замечаний уровня КРИТИЧНО/СУЩЕСТВЕННО)
или «НА ДОРАБОТКУ» со списком, что исправить.
```

### 4.3. Управляющий цикл

```
loop:
  doc      = Агент1(нарушение, факты)
  критика  = Агент2(doc)
  if вердикт(критика) == "ГОТОВ К СУДУ":
      break
  else:
      Агент1 дорабатывает doc с учётом критики   # новая итерация
  # предохранитель: максимум N итераций, затем эскалация человеку
→ send_for_approval.py(doc)   # Human-in-the-Loop, обязательно
```

Готовый документ **никогда** не отправляется автоматически — только через
`send_for_approval.py` после явного одобрения человека (CLAUDE.md §1.5).

## 5. Мониторинг (фоновая ветка)

**Скрипт:** `scripts/monitor_tariffs.py`
- Источники: региональный комитет по тарифам (РЭК), ГИС ЖКХ (dom.gosuslugi.ru),
  публикации об изменениях НПА.
- Действие: сравнить с текущим `data/tariffs.json`; при изменении — записать новую
  версию тарифа с датой вступления и источником, сформировать сигнал в
  `claude-progress.md` (и, при желании, черновик уведомления пользователю).
- Ограничение: только чтение публичных данных; ничего не отправляет.

## 6. Human-in-the-Loop (шлюз исходящих)

**Скрипт:** `scripts/send_for_approval.py`
- Кладёт готовый документ в `data/outbox/` со статусом `PENDING_APPROVAL`.
- Показывает человеку сводку (адресат, суть, требования, способ отправки).
- Отправка/пометка «одобрено» — только по явной команде человека.
- Без approval-флага никакой скрипт харнеса ничего наружу не отправляет.

## 7. Роли субагентов (сводка)

| Субагент | Роль | Где определён |
|---|---|---|
| Классификатор | сортировка входящих | `classify_input.py` + §2 |
| Аудитор начислений | построчная сверка квитанции | `verify_invoice.py` + §3 |
| Юрист-Истец (Агент №1) | составление документа | §4.1 |
| Оппонент/Юрист УК (Агент №2) | состязательная проверка | §4.2 |
| Монитор | тарифы и НПА | `monitor_tariffs.py` + §5 |
| Шлюз согласования | Human-in-the-Loop | `send_for_approval.py` + §6 |
