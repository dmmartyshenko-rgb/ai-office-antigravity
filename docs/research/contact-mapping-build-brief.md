# Бриф сборки: инструментарий «карта связей» (contact-mapping)

Задание для двухмодельной петли `/route` (Fable 5 планирует и ревьюит,
GPT-5.6 Sol реализует). Запуск — на локальном Mac по
`.claude/skills/route/SETUP.md` и `HANDOFF.md` §7. Это черновик спецификации:
Fable на Mac проводит короткое интервью по открытым вопросам (§6) и только
потом пишет `PLAN.md`.

## 1. Контекст

Исследование `docs/research/contact-mapping.md`: проверяем, решает ли
трёхслойное мегакартирование проблему «контактов много, коммуникация не
поддерживается». Пилот (10–15 контактов, 4 недели) не может начаться без
инфраструктуры — её и собираем. Ручное ведение карты умрёт за неделю
(исследовательский вопрос 3), поэтому всё, что можно, делает инструмент.

## 2. Цель сборки

Работающий инструментарий пилота: локальная трёхслойная карта связей
(индекс / карты контактов / журналы) + скрипты, которые делают её ведение
дешёвым. После сборки пользователь может за один вечер завести 10–15
контактов и жить по протоколу пилота.

## 3. Артефакты (что должно существовать)

Код — в репозитории, `tools/contact-map/`:

- `init_contact_map.py` — создаёт локальное хранилище карты (по умолчанию
  `~/contact-map/`, путь настраивается): `INDEX.md`, `contacts/`, `journal/`
  из шаблонов.
- `templates/` — шаблоны трёх слоёв:
  - индекс: строка на контакт — имя/псевдоним, температура
    (тёплая / остывает / остыла), суть связи одной фразой, ссылка;
  - карта контакта: кто и что для него важно; на чём остановились;
    открытые взаимные обещания; **следующее касание** (содержательный
    повод, не «напомнить о себе»); порог остывания в днях;
  - журнал: append-only, свежее сверху.
- `check_contacts.py` — аналог `scripts/check_map.py`: индекс ≤ 60 строк;
  каждый контакт индекса имеет карту и журнал (и наоборот); температура —
  из допустимого списка; у тёплых/остывающих заполнено «следующее касание»;
  список связей, у которых давность последней записи журнала превысила
  порог остывания.
- `capsule.py <контакт>` — «капсула контекста»: карта контакта + последние
  N записей журнала одним текстом, читается за ~30 секунд.
- `tests/` + фикстуры с **вымышленными** контактами; smoke-прогон всех
  четырёх сценариев (init → заполнение → check → capsule).
- `README.md` внутри `tools/contact-map/` — протокол пилота: капсула перед
  контактом, обновление после, еженедельный обзор остывающих.

## 4. Жёсткие ограничения (нарушение = провал ревью)

1. **Приватность.** Реальные имена и данные третьих лиц не попадают в git
   никогда: хранилище карты — вне репозитория (или в каталоге, добавленном
   в `.gitignore` тем же коммитом, что и код). В тестах и примерах — только
   вымышленные люди. Чувствительное (здоровье, конфликты, чужие секреты)
   в шаблонах помечено как «не записываем вовсе».
2. **Гуднарт-защита.** Инструмент нигде не считает «касания в неделю» как
   метрику успеха; check показывает остывание и повод, но не «план по
   общению». Касание без содержательного повода не засчитывается.
3. Только стандартная библиотека Python 3 — без зависимостей, как
   `scripts/check_map.py`.
4. Scope: никаких интеграций (мессенджеры, календарь, разбор переписки) —
   это следующая итерация после пилота.

## 5. Критерий «готово»

- Все тесты зелёные; smoke-прогон четырёх сценариев показан выводом.
- `check_contacts.py` на фикстурах ловит каждое из нарушений §3 (по тесту
  на нарушение) и молчит на валидной карте.
- В git нет ни одного реального имени/контакта (ревьюер проверяет diff).
- Пользователь по README заводит первый вымышленный контакт за ≤ 5 минут.

## 6. Открытые вопросы для интервью перед PLAN.md

1. Где хранить реальную карту: `~/contact-map/` вне git или приватный
   подкаталог репозитория под `.gitignore`? (влияет на бэкап)
2. Рабочий и личный контуры — один индекс или два с первого дня?
3. Пороги остывания по умолчанию для трёх температур (дни)?
4. Язык шаблонов — русский (как мегакарта) или двуязычный?
